# FE-V1-090 Mobile Dashboard Physical Hardening

Date: 2026-07-29
Status: strict criteria frozen before dashboard or Android-harness changes

## Objective

Harden the complete selected Focus Rail mobile dashboard on the target Android phone through private Tailscale Serve HTTPS. This pass binds all 141 canonical states, 39 interactions, 17 workflow paths, 12 journeys, 15 surfaces, and seven approved targets to current package/browser evidence, then requires every canonical interaction and the device-sensitive state subset to run through one no-retry physical acceptance sequence. Narrow prior pairing, prompt, recovery, and remote-security phone runs are inputs, not aggregate completion.

Requirement refs: `FR-002`, `FR-005` to `FR-010`, `FR-016`, `IR-001` to `IR-012`, `NFR-001`, `NFR-002`, `NFR-004`, `NFR-005`, `NFR-011`, `PR-005`, `SFR-001` to `SFR-004`, `SFR-009`, and `SFR-018`.

## Frozen Boundary

- `DEC-028` remains final: all seven Focus Rail rasters, their design system, typed state/interaction contracts, and approved divergences are the only visual target. No Signal Ledger or legacy desktop-board borrowing is permitted.
- Device acceptance uses one committed schema-4 package and the production browser assets, Fastify routes, authentication, SSE, write gate, remote lifecycle, CLI, and service ownership. Test drivers may provide deterministic runtime outcomes but may not replace browser code, bypass HostDeck authorization, intercept requests in Chrome, or use an ADB application tunnel.
- The phone is physically driven through Android accessibility/UI automation and bounded ADB input only. USB is test control, never app transport. Application traffic must use cellular plus the phone Tailscale VPN to private Serve HTTPS while Wi-Fi is disabled.
- All 39 interactions require physical evidence. The current four-project package matrix remains the exhaustive normal/failure owner for all 141 states and 34 browser-owned interactions; physical evidence adds actual viewport, keyboard, touch, accessibility, network, profile, browser, and persistence truth.
- Acceptance cleanup and final user deployment are separate inventories. The acceptance run must restore the device and laptop exactly. The final deployment must intentionally retain only the documented service, Serve, paired authority, and browser state needed to leave HostDeck ready.
