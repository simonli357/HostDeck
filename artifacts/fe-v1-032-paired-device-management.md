# FE-V1-032 Paired-Device Management

Date: 2026-07-26

Status: complete.

## Scope

Implement the selected paired-device list and exact single-device revoke workflow inside the persistent mobile Host & access surface. A current paired reader can inspect one bounded page of devices. A current paired writer can explicitly confirm and revoke one unrevoked device, including an expired device, this phone, or the final active device, with immediate authority invalidation and conservative handling of every unconfirmed outcome.

Excluded: pairing creation or claim changes, permission editing, device renaming, bulk revoke, remote unlock, host-lock implementation, Tailscale/profile/Serve controls, device deletion, total counts, search, arbitrary sorting, local-admin browser authority, CLI changes, API/storage/server changes, automatic retry or polling, durable browser state, a logout alias, complete-dashboard hardening, and physical-phone release acceptance owned by downstream leaves.

## Pre-Change Findings

- `IFC-V1-029` owns exact paired-cookie `GET /api/v1/access/devices`. It accepts only canonical `limit` and opaque cursor query fields, returns at most 100 strictly ascending rows, and exposes only device id, bounded label, permission, created/last-used/expiry/revocation timestamps, continuation, and `has_more`. It has no local-admin safe-GET arm, current-device flag, total, secret, CSRF value, session state, fallback list, partial success, or retry.
- `IFC-V1-059` owns exact `POST /api/v1/access/devices/:device_id/revoke` with `{operation_id, confirmed:true}`. A paired writer or explicit loopback local admin may revoke any active device, including itself and the final device. Paired callers require current CSRF; the host-lock policy is intentionally not applicable. Missing or already-revoked targets conflict.
- A winning revoke durably invalidates the target before success, prevents new target leases, terminates target HTTP/SSE work, and prevents late CSRF publication. A self-revoke success may return its exact receipt after invalidation and clears the device cookie. Terminal-audit or response delivery failure can leave the revoke committed without a success response, so a failed mutation cannot be retried or described as unchanged without a fresh list.
- The current browser coordinator exposes session-oriented protected mutation gating. Its global `writeEligibility` includes host lock, host/runtime health, selected-target currency, and session write authority, so it is not the selected admission rule for device administration. It also has no paired-device list port and does not yet adopt a successful self-revoke immediately.
- The access response already identifies this browser's current device. The list response intentionally does not duplicate a current-device flag, so the browser may mark `This phone` only by an exact same-authority id match in memory. That id need not enter rendered copy, DOM attributes, logs, screenshots, or artifacts.
- Device-list cursors remain valid when rows are revoked or deleted. This permits an explicit refresh of the current page after a conflict or uncertain outcome without accumulating an unbounded client-side list.
- `DEC-028` selects Focus Rail and rejects Signal Ledger borrowing or additional structural drift. The executable mobile contract assigns `access_device_list` and `confirm_revoke` to Host & access and confirmation states. The raster set does not contain a literal device-list panel, and this typed state was not marked mockup-required; the selected component mapping therefore owns a flat in-sheet device rail plus the existing Focus Rail confirmation sheet, not a new route or desktop inspector.
- The existing Host & access owner is mounted above the Radix sheet portal, which is the correct lifetime for one device-list/revoke controller. Sheet dismissal must not create a second owner, cancel a dispatched revoke, or lose an uncertain-outcome latch.

## Frozen Design

### Exact Browser Boundary

- Add only two narrow coordinator operations: one paired-device list read and one paired-device revoke. Neither exposes the generic HTTP client, cookie, CSRF token/generation, origin headers, or server adapter to React or the headless device controller.
- Device-list admission requires current exact paired-device access for this browser. It does not require writer permission, current host health, an unlocked host, current selected-session data, or a session stream. A list response is accepted only while the same paired-device authority and configured origin remain current.
- Device-revoke admission requires current exact paired-writer access and ready page CSRF. It deliberately does not use session `writeEligibility`, host lock, runtime readiness, selected target, or stream state. Every request is one exact target, one fresh validated operation id, one `confirmed:true` body, and zero automatic retries.
- The coordinator validates response operation id, target device id, `authority_invalidated:true`, and `self_revoked` against the request and current browser identity before exposing success. A contradictory or malformed successful response is an unconfirmed mutation outcome, never a usable success.
- An authority denial while reading devices invalidates page CSRF, closes the stream, purges protected host/target data, and retains at most stale access metadata until the normal access route proves current truth. Transport or server failure alone does not fabricate authority loss.

### Bounded List State

- One persistent headless controller owns list phase, one current page, its private input cursor, page ordinal, one list request, one revoke request, one confirmation, one result, and close/suppression state. It consumes only coordinator snapshot/list/revoke ports plus injected operation-id and clock functions.
- The first current paired authority starts one list read. The UI requests exactly 20 rows per page. `Next page` replaces the current rows using the returned opaque cursor; `Start over` reloads the first page. It does not append pages, retain arbitrary page history, infer totals, jump by offset, search, sort, poll, prefetch, or create a second list client.
- Every page is independently checked against its request: at most 20 rows, strict response order, every id after the decoded input cursor, coherent nonempty/full continuation, and exact final-row cursor. Malformed or cross-page responses fail closed with no partial rows.
- A same-page load is single-flight. Duplicate click/touch/Enter, rerender, sheet close/open, StrictMode replacement, and concurrent reload/next/start-over cannot create another request. Page controls and revocation remain disabled while a replacement page is unresolved.
- A same-authority list failure retains a previously proven page only as visibly stale and disables every revoke until an explicit successful reload. With no prior page, failure is not rendered as an empty list. There is no timer, background retry, exponential backoff, cached fallback, browser storage, URL state, or service worker.
- Authority identity or origin replacement, current access loss, expiry, external revoke, coordinator close, or controller close aborts/suppresses list work and purges all rows, private ids, cursors, and confirmations. Session route changes with the same paired authority do not recreate the owner or duplicate the list.

### Device Presentation

- Preserve server order. Each rendered row has a bounded normalized client label or `Unlabeled device`, a page-local `Device N` cue that distinguishes duplicate labels without rendering the internal id, permission, current-device marker when exactly proven, last-used truth (`Never` when null), and Active, Expired, or Revoked state. Revoked outranks expired.
- Raw device ids remain internal correlation keys. They are absent from visible copy, DOM ids/data attributes, accessible names/descriptions, live regions, logs, browser storage, URLs, screenshots, and evidence. The page-local cue is not a credential, count, or durable identity.
- Read-only callers see the exact same authorized page but no revoke command. Writers may revoke every unrevoked row, including an already-expired device, this phone, and a proven final active device. Host lock does not disable revoke. Only already-revoked rows cannot enter confirmation.
- `Last active device` is shown only when the first page is terminal and that complete returned set proves exactly one active non-expired device. A later page, a nonterminal page, or a stale page cannot claim final-device status.

### Exact Revoke State Machine

- Selecting revoke snapshots one exact row and opens one nested Focus Rail confirmation. Duplicate labels are disambiguated by the page-local cue. A changed page, changed authority, refreshed row, newly revoked row, or dismissed confirmation invalidates the selection before dispatch.
- The ordinary confirmation states that the named current device will immediately lose HostDeck reads, writes, and live updates. An expired target instead says that its already-expired pairing will be permanently revoked. Self-revoke says `This phone`, explains that this browser will immediately lose access, and requires a new laptop pairing. A proven final-device warning explains that a new pairing link will be required. No wording implies device deletion, Tailscale removal, OS sign-out, remote unlock, or cancellation of Codex work.
- Operation-id generation occurs only after the explicit confirm command and before dispatch. Invalid generation is a known local failure and sends no request. Once dispatch begins, close/Escape/outside/cancel and all list/page/revoke controls are disabled until the one request settles or its owner is suppressed.
- A correlated other-device success patches only that exact row to the server-returned revocation timestamp, announces success once, and prevents another revoke of the row. It does not infer changes to other rows or automatically reload.
- A correlated self-revoke success immediately advances coordinator authority, aborts pending coordinator reads, invalidates CSRF, closes the active/opening stream, purges protected host/target data, blocks every current and late protected operation, and exposes current revoked access truth before the revoke promise resolves. The device controller purges the list but may retain one bounded `This phone was revoked` result with laptop-pairing recovery copy.
- Any failed or malformed self-revoke after dispatch is authority-uncertain: the coordinator immediately invalidates CSRF, closes the stream, purges protected data, and requires an explicit access refresh before protected disclosure can return. It never assumes that this phone remained paired.
- A `409` for another target is a known conflict but leaves the page stale because the row changed outside this snapshot. Transport loss, timeout, abort, `5xx`, terminal-audit failure, malformed/cross-target response, or any other post-dispatch failure is an unconfirmed outcome. Both states disable further revokes until an explicit successful same-page reload proves active/revoked truth; no request is replayed and the old operation id is never reused.
- Target authority loss during another-device revoke clears the authorized list and suppresses late row/result publication. Closing the React/controller owner observes every pending rejection and permits no stale publication, duplicate dispatch, unbounded waiter, or unhandled promise.

### Focus Rail Surface

- Keep one mobile-first Host & access bottom sheet. Add one unframed `Paired devices` section after the existing access facts/recovery band, separated by the selected rail divider. Do not add a route, tab, nested card, desktop side panel, table, terminal-style identifier, hover-only control, Option A component, or second sheet scroll owner.
- Loading, empty, current, stale, page failure, loading-next, read-only, page-security-required, confirmation, revoking, success, conflict, uncertain, expired, revoked, self-revoked, and access-lost states use fixed bounded copy and Lucide icons. Empty is shown only after a successful terminal empty page.
- Revoke uses an icon button with an exact accessible name and at least 44 px target. Page commands use familiar refresh/next/start-over icons with text where the command would otherwise be ambiguous. Confirmation uses explicit Cancel and destructive Revoke commands; destructive color never carries meaning alone.
- The nested confirmation owns title, description, target, consequence, optional final-device warning, busy state, and focus. Focus enters the confirmation, cannot escape while dispatch is active, and returns to the originating row when still present; self-revoke/access loss returns to the outer sheet's safe close/header target.
- At 320, 360, 390, 412, 768, and 1280 widths, 390 x 420 short height, long 120-character labels, duplicate/unlabelled devices, 20 rows, and actual 200 percent reflow, the sheet close, list state, row metadata, page controls, revoke target, confirmation actions, and underlying route remain reachable without horizontal overflow, overlap, clipping, or competing scroll containers.
